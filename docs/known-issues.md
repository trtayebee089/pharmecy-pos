# Red Pharma POS: Known Issues Register

**System:** Red Pharma POS. A legacy Laravel 10.48.29 Blade app derived from SalePro.
**Codebase audited (read-only):** `D:\01 REDPHARMA\00 CODEBASE\backend - ocr pos\`. Every `file:line` below is relative to this folder unless stated otherwise.
**Sources merged:** WP1 `wp1-navigation-core.md`, WP2 `wp2-navigation-admin.md`, WP3 `wp3-database.md` (production dump dated 2026-03-10), WP4 `wp4-api-consumers.md`, WP5 `wp5-workflows-security.md`, plus production checks made by the lead auditor on 2026-11-23.
**Register date:** 2026-11-23
**Companion document:** `pos-business-workflows.md` explains how each issue shows up inside a business workflow.

**How to read this register**

- **Severity**
  - **Critical:** exploitable remotely, or causes silent loss of data, money or stock at scale.
  - **High:** a serious integrity or security risk that needs some precondition.
  - **Medium:** a correctness or hardening gap.
  - **Low:** hygiene.
- **Fix-in-legacy-now?**
  - **Yes:** patch the running legacy system now, without waiting for the rebuild. Every Critical issue that can be exploited in production today is Yes.
  - **Advised:** a cheap, high-value patch that should still be made in legacy.
  - **No:** fix it in the new system.
- **Verification tags**
  - **[PROD]:** verified against production. Only HEAD/GET status checks were made; no data was downloaded and nothing was changed.
  - **[V]:** verified in the local source code.
  - **[U]:** unverified. It depends on production code, config, cron or data that has not been inspected.
- **Production differs from both local snapshots (see KI-017).** Live `/pos` responds with 302, while `/report/pos` returns 404. Every code-level finding is therefore proven for the local snapshot only, and must be re-checked against the real production source before anyone fixes it there.
- No secret values or personal data are reproduced anywhere in this document.

## Immediate production actions

Do these in order, starting now. Several can be done as **web-server deny rules** (`.htaccess` or the hosting panel) without deploying any code. That matters because the exact production source is not in the local workspace (KI-017, KI-018).

1. **Remove the public database backups (KI-001).** Take `salepro_backup_1689056748.sql` and `salepro_backup_1738037751.sql` out of the web root immediately. Both currently return HTTP 200 `text/x-sql` on `pos.redpharmabd.com`. At the same time:
   - Add a deny rule for `*.sql`, `*.zip`, `*.log`, `*.env` and `*.txt` in `public/`.
   - Pull the web-server access logs for any GET on these files.
   - **Treat the dumps as already leaked.** Rotate the DB credentials and every secret that could be inside them (SMTP, SMS and payment keys held in `pos_setting`, `mail_settings` and `external_services`). Force staff password resets. Revoke customer API tokens if customer data is present.
   - Assess breach-notification duties. Pharmacy purchase history is sensitive health data. The dump contents were deliberately not inspected.
   - Also delete `public/delete.php`, `public/debug_payroll_params.txt` and `public/vendor/tinymce.zip` (KI-020).
2. **Block the unauthenticated kill switches and installers at the web server before anything else (KI-003, KI-005, KI-006, KI-021, KI-022).** Deny these paths:
   - `/update-coupon`, `/migrate`, `/cc`, `/auto-update-dashboard`
   - `/developer-section*`, `/new-release`, `/bugs`, `/version-upgrade`, `/bug-update`
   - `/saas/install*`, `/woocommerce-install`, `/ecommerce-install`, `/addon-list`
   - `/phpfileinfo`, `/setting/backup`, `/backup`, `/setting/empty-database`

   Then search the access logs for hits on any of these paths. **Do not test `/update-coupon` on production.** It truncates every table and deletes directories.
3. **Check the scheduler before anyone enables cron (KI-004, KI-042).**
   - Run `crontab -l` on the host and look for `schedule:run`.
   - If cron is **not** running, keep it off until `reset:db`, `purchase:auto` and `quote:daily` have been removed from `app/Console/Kernel.php`.
   - If cron **is** running, check whether the production Kernel still schedules `reset:db`, because the DB evidently survives today. Also look for phantom `pr-` purchases created by `purchase:auto`.
4. **Restore the storefront API for the live website (KI-002).** The `redpharmabd.com` bundle calls `https://pos.redpharmabd.com/api`, and every catalogue endpoint there returns 404. `api.redpharmabd.com` does not resolve (NXDOMAIN). Choose one fix:
   - deploy the `routes/api.php` surface onto the POS host, or
   - rebuild the website against the working API host, which web-v2 and the Flutter app use: `redpharma-api.techrajshahi.com`.

   Then confirm which database receives web orders (KI-033).
5. **Stop executable uploads (KI-008).**
   - Add a "no PHP execution" rule to `public/documents/`, `public/stock_count/`, `public/images/` and every other upload directory.
   - Scan those directories for `.php`, `.phtml` and `.phar` files.
6. **Close privilege escalation (KI-009, KI-010, KI-025, KI-026).**
   - Restrict role and user write routes (`role/*`, `user/*` update, `user/update_profile/*`) to admins.
   - Turn off self-registration with `Auth::routes(['register' => false])`.
   - Review every user's `role_id` and `is_active` for unexpected admins.
   - Reset the passwords of supplier-login (role 6) users, which may still use the hard-coded default.
7. **Close the order-data leak (KI-012, KI-013).**
   - Require a token and an ownership check on `GET /api/orders/{id}` and `/api/customer/orders/{id}`.
   - Refuse `reward_points` on unauthenticated checkout.

   Apply this on whichever host actually serves the API.
8. **Recover the true production source (KI-017, KI-018).** Copy the live code tree read-only (via SSH or the hosting panel) into a fresh git repository, excluding `.env` and uploads. The local snapshots differ from production, and the `deployment-work/github-pos` clone is corrupt. No legacy fix should be written until this baseline exists.
9. **Take a verified, off-web-root backup** of the database and files before applying any of the code fixes in the register below.
